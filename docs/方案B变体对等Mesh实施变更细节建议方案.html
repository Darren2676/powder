一、方案概述

1.1 核心理念

总部不设独立中心数据库，总部和所有工厂地位完全对等。每个节点（含总部）都拥有完整的本地 SQL Server 实例，节点之间相互同步全部业务数据。总部只是网络中的一个"普通节点"，通过自身本地库即可查看全系统汇总报表。

1.3 与原方案 B 的关键区别

维度原方案 B (星型)方案 B 变体 (对等 Mesh)
中心节点总部有独立中心库无中心节点，全员对等
数据流向工厂→总部单向上报所有节点互相同步
总部角色数据汇总者+主数据下发者普通节点，与其他厂相同
总部断网无法汇总，但各厂正常总部离线后恢复时补同步
主数据维护总部独占修改任一节点可改，变更广播
每个节点数据量总部全量，工厂仅自己每个节点全量
跨厂查询需汇总库/Linked Server查本地库，零延迟

三、编号生成层改造（核心改造，影响面最广）

3.1 当前问题

所有编号生成函数都使用 SELECT MAX(xxx_number) as max_num FROM 表 WHERE xxx_number LIKE :prefix 模式。在单库场景下不会冲突，但在对等 Mesh 中：

  • 每个节点只写入自己 site_prefix 的数据，编号查询时需增加 WHERE site_prefix = :sitePrefix 条件
  • 编号格式需加入站点前缀，如 M-HF-20260515-001

3.2 改造方式

改造前（以 generateProductionNumber 为例）：
  prefix = 'M' + YYYYMMDD
  SELECT MAX(production_number) FROM Production_plan WHERE production_number LIKE prefix+'%'
  → M20260515001

改造后：
  sitePrefix = process.env.SITE_PREFIX    // 如 'HF'
  prefix = 'M-' + sitePrefix + '-' + YYYYMMDD + '-'
  SELECT MAX(production_number) FROM Production_plan 
    WHERE production_number LIKE prefix+'%' AND site_prefix = :sitePrefix
  → M-HF-20260515-001
建议：先抽取一个统一的编号生成基础函数 generateNumber(table, column, prefix, sitePrefix, transaction)，减少重复代码。统一改造入口后再加站点前缀，避免遗漏。

八、日常数据变更细节

8.1 数据写入流程（改造后）

用户在工厂A提交报工单：
  1. Controller 接收请求
  2. siteGuard.middleware 校验 → 自动注入 site_prefix='A'
  3. 编号生成 → WR-A-20260515-001
  4. INSERT work_report (..., site_prefix='A', version=1)
  5. INSERT sync_log (table='work_report', record_id='WR-A-20260515-001', 
       operation='C', source_site='A', status='pending')
  6. EventBus.emit('WorkReportCreated', {..., site_prefix: 'A'})
  7. 同步服务检测到 pending sync_log → 推送到 SYNC_PEERS

8.2 数据同步流程

定时轮询（每30秒）：
  1. 查询 sync_log WHERE status='pending' AND retry_count < 3
  2. 按 target_site 分组打包
  3. POST /api/sync/push → 各 peer
  4. peer 接收后：
     a. 检查 version：若本地 version >= 远程 version → 冲突，写入 sync_conflict_log
     b. 若本地不存在或 version < 远程 → UPSERT + version = 远程 version
     c. 写入 sync_log 本地（标记 source_site 为来源）
  5. 推送成功 → 更新 sync_log.status = 'synced'
  6. 推送失败 → retry_count++，下次重试

8.3 各数据类型同步策略

数据类型涉及表归属同步方向同步频率
基础数据（物料、客户、供应商、BOM、工艺路线等）item_master, customer, supplier, bom_header, routing_header 等任一站点可创建全 Mesh 广播实时（变更即推）
生产数据（计划、报工、入库）Production_plan, work_report, production_inbound_order 等创建站点归属全 Mesh 广播准实时（30秒）
库存数据material_inventory, lineside_inventory 等仓库所属站点全 Mesh 广播准实时（30秒）
销售订单sales_order, sales_order_detail创建站点归属全 Mesh 广播实时
采购订单purchase_order, purchase_req创建站点归属全 Mesh 广播准实时
质量数据production_inspection, nonconforming_product 等检验站点归属全 Mesh 广播准实时
用户/权限users, role, permission 等任一站点可改全 Mesh 广播实时
财务数据standard_cost_header, piece_rate_wage_header 等创建站点归属全 Mesh 广播每小时
文件附件uploads/ 目录上传站点归属rsync/API每5分钟

8.4 冲突处理策略

冲突场景发生概率处理方式
两站同时修改同一基础数据（如同名客户）中乐观锁：version 不匹配 → 拒绝后到达的变更，写入 sync_conflict_log，提示用户手动合并
网络分区后，同一记录被两地修改低LWW（Last-Write-Wins）：以 updated_at 时间戳为准，自动合并，记录到 sync_conflict_log 供人工复核
编号重复极低站点前缀天然隔离，不冲突
从节点上线后大量积压同步低全量快照 + 增量：新节点先 GET /api/sync/snapshot 获取全量，然后切换到增量同步

8.5 汇总报表查询方式

-- 总部用户查看全系统生产计划（查本地库，零跨库延迟）
SELECT 'HQ' AS site, * FROM Production_plan WHERE site_prefix = 'HQ'
UNION ALL
SELECT 'A'  AS site, * FROM Production_plan WHERE site_prefix = 'A'
UNION ALL
SELECT 'B'  AS site, * FROM Production_plan WHERE site_prefix = 'B'
UNION ALL
SELECT 'C'  AS site, * FROM Production_plan WHERE site_prefix = 'C'
ORDER BY production_number;

-- 工厂A用户执行同一条 SQL，同样能看到全系统数据
-- （因为工厂A也同步了 HQ/B/C 的数据）
→ 每个节点都有完整副本

十、关键风险与应对

风险影响应对措施
40+ 表加 site_prefix 字段，历史数据需回填大表 ALTER 可能锁表分批执行，低峰期操作；默认值填充当前站点前缀
编号格式变更，前端/报表中硬编码的编号解析失效现有数据编号无站点前缀新旧编号兼容：旧数据 site_prefix 回填但编号不变，仅新数据使用新格式
全量数据同步导致网络/磁盘压力每节点存储 = 单厂数据 × 节点数橡胶密封件行业数据量小，4节点约200GB，普通服务器可承载
同步延迟导致用户看到过期数据操作失误前端展示数据来源站点 + 最后同步时间；非归属数据加"同步于XX:XX"标签
同步服务单点故障某个节点同步中断sync_log 持久化 + 重试机制；节点恢复后自动补偿积压数据
网络分区期间多节点同时修改基础数据数据冲突乐观锁 + LWW 自动合并 + 人工仲裁兜底
