一、现状分析

1.1 现有批次号生成机制

当前系统中，成品批次号（FB前缀）仅在生产入库环节由 generateBatchNumber('FB', factoryCode, transaction) 函数生成：

1.2 现有编号格式

批次类型前缀格式示例
成品批次FBFB-{工厂编码}-{YYYYMMDD}-{序号}FB-N-20260609-001
原料批次MBMB-{工厂编码}-{YYYYMMDD}-{序号}MB-N-20260609-001
半成品批次HBHB-{工厂编码}-{YYYYMMDD}-{序号}HB-N-20260609-001

1.3 序号管理

使用 batch_number_sequence 表管理每日递增序号，按 prefix 键（如 FB-N-20260609-）查询当前序号并自增，保证同一天同类型同工厂不重复。

1.4 痛点

  • 无法提前追溯：批次号在入库时才产生，生产过程中无法用批次号关联计划→派发→报工→入库全链路
  • 批次号与计划编号脱节：FB-N-20260609-001 与 M20260609001（生产计划编号）无逻辑关联
  • 部分客户需求：某些客户/产品需要以计划编号为基准的批次号，便于从批次号直接反查生产计划
  • 拆分追溯需求：生产单拆分后，需要区分不同子单的批次号（追加 -S01/-S02 序号），或保持统一批次号

二、两种模式对比

🔵 模式A：入库时自动生成（现有）

  • 触发时机：生产入库确认时
  • 编号格式：FB-{FC}-{日期}-{序号}
  • 优点：简单、无需预分配、入库数量确定后编号
  • 缺点：无法提前追溯，与计划编号无关联
  • 适用场景：通用产品、无追溯要求的常规入库

🟢 模式B：计划派发时预生成（新增）

  • 触发时机：生产计划拆分/派发时
  • 编号格式：FB-{计划编号}[-S{nn}]
  • 优点：可提前追溯，批次号与计划强关联
  • 缺点：需预分配，入库数量可能变化
  • 拆分序号：可配置是否追加 -S01/-S02 序号
  • 适用场景：需追溯的定制产品、汽车件等
💡 核心设计原则：两种模式并存，由"产品批次号产生规则"配置决定每个产品使用哪种模式。未配置的产品默认使用模式A。模式B支持拆分追加序号开关：开启时拆分子单各自独立批次号（-S01/-S02），关闭时所有拆分子单共享同一批次号。

三、模式A：入库时自动生成（现有）

模式A保持现有逻辑不变，generateBatchNumber('FB', factoryCode, transaction) 在 productionInboundFinished 被调用时生成批次号：

flowchart TB subgraph 入库流程 START["生产入库请求"] --> CHK["校验生产单状态"] CHK --> GEN["generateBatchNumber('FB', factoryCode)"] GEN --> FB_NO["生成: FB-N-20260609-001"] FB_NO --> WRITE1["写入 finished_batch_inventory"] WRITE1 --> WRITE2["写入 inventory_transaction"] end

此模式下，成品批次号格式为 FB-{工厂编码}-{YYYYMMDD}-{序号}，序号由 batch_number_sequence 表管理。入库时生成，无需改动。

编号规则：
- append_split_seq=1（默认）：未拆分→FB-{production_number}，拆分→FB-{production_number}-S01、-S02

- 拆分序号仅在 splitOrdersCore 时分配

⚠️ 一致性保证：
- 模式B的批次号在拆分/派发时已写入 production_order，入库时只读取，不会重新生成
- 模式B下如果 preassigned_batch_number 为空（异常情况），降级为模式A自动生成
- 撤回入库时，模式B的预分配批次号不清除（因为生产单仍存在），仅清除库存记录

// --- lookupBatchRule: 查询产品批次号规则 ---
async lookupBatchRule(itemNumber, factoryId?, transaction?):
  // 1. 精确匹配: item_number + factory_id
  if (factoryId !== null):
    row = SELECT TOP 1 batch_rule_mode, batch_number_template,
                   ISNULL(append_split_seq, 1) AS append_split_seq
            FROM batch_number_rule_config
            WHERE item_number = :item_number
              AND factory_id = :factory_id AND is_active = N'是'
    if (row) return { mode: row.batch_rule_mode, template: row.batch_number_template,
                      append_split_seq: !!row.append_split_seq }

  // 2. 全局匹配: item_number + factory_id IS NULL
  row = SELECT TOP 1 ... FROM batch_number_rule_config
        WHERE item_number = :item_number AND factory_id IS NULL AND is_active = N'是'
  if (row) return { mode, template, append_split_seq }

  // 3. 无配置 → 默认模式A
  return null

// --- generatePreassignedBatchNumber: 模式B预分配批次号 ---
generatePreassignedBatchNumber(productionNumber, splitIndex?, appendSplitSeq = true):
  base = "FB-{productionNumber}"
  if (appendSplitSeq && splitIndex > 0):
    return "{base}-S{splitIndex:02d}"    // FB-MN20260609001-S01
  return base                               // FB-MN20260609001

// --- resolveBatchNumber: 入库时统一入口 ---
async resolveBatchNumber(params: { itemNumber, factoryId, productionOrderNumber, factoryCode, transaction }):
  rule = await lookupBatchRule(itemNumber, factoryId, transaction)
  if (rule?.mode === 'B'):
    po = SELECT preassigned_batch_number FROM production_order
         WHERE production_order_number = :pon
    if (po?.preassigned_batch_number):
      return po.preassigned_batch_number    // 模式B
    // 降级: 预分配为空
    log.warn('模式B但预分配为空, 降级为模式A')
  return generateBatchNumber('FB', factoryCode, transaction)  // 模式A

十二、边界场景与异常处理

场景处理策略
模式B但 preassigned_batch_number 为空降级为模式A自动生成，并记录警告日志
同一生产单多次入库（部分入库）模式B：使用同一预分配批次号（与生产单 1:1）
模式A：每次入库生成新批次号
拆分后又撤回入库预分配批次号不清除，仅回退库存记录
append_split_seq=0 且拆分多单所有拆分子单共享同一批次号 FB-{production_number}，入库时均使用此批次号
append_split_seq 从1改为0（或反之）仅影响后续新拆分/派发的生产单，已有生产单的 preassigned_batch_number 不变
规则从模式B改为模式A已预分配的批次号保留不影响，仅影响后续新单
规则从模式A改为模式B仅影响新的拆分/派发，已有生产单不会追溯生成
删除规则物理删除，不影响已使用批次号的数据
退货入库退货入库不生成新批次号，使用原出库批次号（两种模式均如此）
异常出入库（盘盈入库）不受规则影响，始终用 generateBatchNumber('FB') 自动生成
factory_id 中间件自动注入auth.middleware 在 POST/PUT 时自动注入 factory_id，控制器需识别 0/null/'' → DB NULL

13.3 技术要点

实施过程中的关键技术决策：
- SQL Server 兼容：分页使用 ROW_NUMBER() OVER() 而非 OFFSET...FETCH（兼容2008+）
- API 前缀：system 域路由直接挂载，路径为 /api/v1/batch-number-rules（无 /system 前缀）
- factory_id 处理：中间件自动注入 factory_id，控制器识别 0/null/'' → DB NULL
- 产品编号搜索：使用 a-select show-search + 300ms防抖，调用 item-masters API
- 唯一约束：两个筛选索引（factory_id NOT NULL + factory_id IS NULL），确保同一产品同工厂仅一条规则
