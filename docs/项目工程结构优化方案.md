## 一、现状分析

### 1.1 后端现状（server/src/）

| 项目 | 当前状态 | 问题 |
|------|---------|------|
| controllers/ | 79 个文件平铺 | 超过 70 个文件在同目录，查找和维护困难 |
| routes/ | 76 个文件平铺 | 同上，且 index.ts 导入 70+ 路由 |
| services/ | 仅 3 个文件 | 业务逻辑直接写在 controller 中，缺乏 Service 层 |
| validators/ | 空目录 | 无输入校验层 |
| models/ | 仅 3 个文件（User、Notification、index） | 用 raw SQL 替代 Sequelize Model，无集中模型管理 |
| middleware/ | 4 个文件 | 结构合理 |
| utils/ | 7 个文件 | 结构合理 |
| 迁移脚本 | 32 个散布在 src/ 和 src/scripts/ | 无统一管理 |

```typescript
export interface PaginationParams {
  page?: number
  limit?: number
}

export interface PaginationResult {
  total: number
  page: number
  limit: number
  totalPages: number
}

export function parsePagination(query: any): { offset: number; limit: number; page: number; pageSize: number } {
  const page = Math.max(1, parseInt(query.page as string) || 1)
  const pageSize = Math.max(1, parseInt(query.limit as string) || 20)
  return { offset: (page - 1) * pageSize, limit: pageSize, page, pageSize }
}

export function buildPaginationResult(total: number, page: number, pageSize: number): PaginationResult {
  return { total, page, limit: pageSize, totalPages: Math.ceil(total / pageSize) }
}
```

## 七、迁移策略

由于项目已有大量功能在线运行，**不建议一次性重构**。应采用渐进式迁移，确保每个步骤都可回滚。

### 阶段 1：创建基础设施（不影响现有代码）

| 步骤 | 操作 | 风险 |
|------|------|------|
| 1.1 | 创建 `AGENTS.md` | 无风险，纯新增 |
| 1.2 | 创建 `ecosystem.config.js` | 无风险，纯新增 |
| 1.3 | 创建 `.env.example` | 无风险，纯新增 |
| 1.4 | 创建 `modules/` 目录结构（空壳，含所有域子目录和 index.ts） | 无风险，纯新增 |
| 1.5 | 创建 `shared/` 目录，将 `middleware/`、`utils/`、`types/` 复制到 `shared/` 下 | 无风险，复制而非移动 |
| 1.6 | 创建 `sql/migrations/` 目录 | 无风险，纯新增 |
| 1.7 | 创建 `config/constants.ts` 和 `shared/utils/pagination.ts` | 无风险，纯新增 |

**验证标准：** 现有代码编译和运行完全不受影响。

### 阶段 2：逐域迁移后端（按业务域逐一搬迁）

**迁移顺序**（从最稳定、依赖最少的域开始）：

| 优先级 | 域 | 原因 |
|--------|-----|------|
| 1 | master-data | 模块最多（23个），无跨域依赖，最稳定 |
| 2 | system | 核心基础，但涉及认证需谨慎 |
| 3 | finance | 仅 1 个模块，最简单 |
| 4 | planning | 3 个模块，逻辑较独立 |
| 5 | sales | 7 个模块，依赖 master-data |
| 6 | warehouse | 5 个模块，依赖 master-data |
| 7 | purchasing | 5 个模块，依赖 master-data + warehouse |
| 8 | quality | 9 个模块，相对独立 |
| 9 | production | 8 个模块，依赖最多（master-data + planning + warehouse） |
| 10 | integration | 3 个模块，外部集成 |

**每个域的迁移步骤（以 master-data 为例）：**

1. 将 `controllers/customer.controller.ts` 移动到 `modules/master-data/customer/customer.controller.ts`
2. 将 `routes/customer.routes.ts` 移动到 `modules/master-data/customer/customer.routes.ts`
3. 更新 `customer.routes.ts` 中的 import 路径（controller 引用从 `../../controllers/customer.controller` 变为 `./customer.controller`）
4. 在 `modules/master-data/index.ts` 中注册该域所有路由
5. 更新 `routes/index.ts`：删除旧的平铺 import，改为 `import masterDataRoutes from '../modules/master-data'`
6. 执行 `npx tsc --noEmit` 验证编译
7. 启动服务验证 API 功能正常

**验证标准：** 每个域迁移后，API 路径不变，功能完全一致。

### 阶段 3：前端同步迁移

| 步骤 | 操作 | 风险 |
|------|------|------|
| 3.1 | 创建 `api/` 子目录结构（system/、master-data/、...） | 无风险 |
| 3.2 | 逐域移动 API 文件到对应子目录 | 低风险，需更新 views 中的 import 路径 |

| 3.6 | 更新 router 中的 component import 路径 | 中风险，需逐一验证 |
| 3.7 | 执行 `npx vue-tsc --noEmit` 验证编译 | — |

**验证标准：** 每个域迁移后，页面路由路径不变，UI 功能完全一致。

## 八、迁移风险评估

| 风险 | 影响程度 | 发生概率 | 缓解措施 |
|------|---------|---------|---------|
| 导入路径变更导致编译失败 | 高 | 中 | 每次只迁移一个域，迁移后立即 `tsc --noEmit` 验证 |
| 前端路由路径变更影响用户书签 | 低 | 低 | 路由 URL 路径不变，只变内部文件组织 |
| API 路径变更影响前端调用 | 低 | 低 | API URL 不变，只变内部文件组织 |
| 迁移过程中功能回归 | 中 | 中 | 每个域迁移后运行端到端验证 |
| 大文件迁移遗漏 | 中 | 中 | 使用 Git 跟踪所有文件变更，迁移前 commit |
| 3 个无路由的控制器迁移 | 低 | 低 | itemAttachment、purchaseInspection、unitConversion 需确认是否需要补全路由 |

**核心原则：外部接口（API URL、路由路径）不变，只改变内部代码组织结构。**

## 九、迁移前的准备工作

在开始迁移之前，务必完成以下准备：

1. **Git 提交当前所有改动** — 确保当前代码状态有备份
2. **创建迁移分支** — `git checkout -b refactor/project-structure`
3. **记录当前 API 路径清单** — 以便迁移后验证所有 API 仍然可用
4. **记录当前前端路由清单** — 以便迁移后验证所有页面仍可访问
5. **准备回滚方案** — 如果某个域迁移失败，可以 `git revert` 回退
