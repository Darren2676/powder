## 一、方案概述

### 1.1 业务背景

在MES系统中，生产单从创建到执行需要经历一个完整的审批和派发流程。派发是将已审批的生产单正式下达到车间执行的关键环节，派发时需要同步生成工序任务、备料清单以及委外申请，并将生产状态回写至销售订单，以便车间进行生产准备和销售端同步进度。

### 1.2 功能目标

实现**一键派发**功能，在同一个事务中完成以下操作：

1. **排产冲突检查** — 本批次内冲突（400）+ 数据库已派发记录冲突（409）双层拦截
2. **派发生产单** — 更新生产单状态为"已派发"，同时写入设备、模具、班次等调度信息，并记录 baseline 基线字段
3. **自动生成工序任务** — 根据产品匹配的工艺路线，自动拆解为工序任务，审批状态直接置为"已审批"
4. **自动生成委外申请** — 对工序中标记为 `is_outsourced` 的节点，自动生成委外申请单
5. **自动生成备料单** — 根据产品或工艺路线关联的BOM，获取第一层物料明细并计算需求量，审批状态直接置为"已审批"
6. **销售订单回写** — 调用 `syncProductionStatus` 将生产状态回写到关联的销售订单明细

### 1.3 业务流程图

## 二、前置条件与业务规则

### 2.1 派发前置条件

| 条件 | 说明 | 校验层级 |
|------|------|----------|
| 审批状态 = "已审批" | 只有审批通过的生产单才能派发 | 前端 + 后端双重校验 |
| 计划状态 = "未开始" | 已派发或已完成的生产单不能重复派发 | 前端 + 后端双重校验 |
| 生产单存在 | 生产单编号必须有效 | 后端校验 |
| 排产资源不冲突 | 设备+生产日期+班次组合不能与本批次或数据库内已派发记录冲突 | 后端校验（400/409） |

### 2.2 工序任务生成规则

| 规则 | 说明 |
|------|------|
| 工艺路线匹配 | 根据生产单的 `item_number` 匹配 `routing_header`，优先取 `is_primary=1` 的主工艺路线，否则按 `creation_date DESC` 取最新启用且已审批的路线 |
| 去重保护 | 同一生产单 + 同一工序号不会重复生成（幂等性） |
| 编号格式 | `PT-YYYYMMDD-NNN`，如 `PT-20260317-001` |
| 初始状态 | `task_status = '未开始'`，`approval_status = '已审批'`（派发自动审批），`inspect_status = '无需检'` |
| 委外自动触发 | 工艺路线明细 `is_outsourced = 1` 的工序，同步在 `outsourcing_req` / `outsourcing_req_detail` 生成委外申请 |
| 操作人字段 | `operator` 优先取 `routing_detail.operator`，否则取当前登录用户 |
| 备注字段 | `remark` 来自 `routing_detail.remark` |

### 2.3 备料单生成规则

| 规则 | 说明 |
|------|------|
| BOM匹配 | 优先按 `routing_header.bom_number` 直接查询 `bom_header`；无关联时退化为按 `item_number` 匹配 `bom_header`（启用且已审批，版本号倒序） |
| BOM展平 | **仅取 `bom_detail` 第一层明细**（不递归展开子BOM，与原方案"递归10层展平"不同，见第十一章差异说明） |
| 物料汇总 | 按 `material_number` 去重合并（同物料在多行出现时累加） |
| 需求量计算 | `需求量 = (计划数量 / BOM基数量) × 物料标准用量`（保留4位小数） |
| 工作中心来源 | 优先通过 `routing_detail_material` 映射到对应工序，取其 `work_center_number`；无映射时回退到 `bom_detail.step_number` 对应工序 |
| 倒冲标识 | 透传 `routing_detail_material.is_backflush`，用于领料冲销 |
| 去重保护 | 同一生产单已存在备料单时跳过（幂等） |
| 清理机制 | 主表插入成功但明细写入失败时，自动回滚删除孤立的备料单主表行 |
| 编号格式 | `MP-YYYYMMDD-NNN`，如 `MP-20260317-001` |
| 初始状态 | `preparation_status = '未领料'`，`approval_status = '已审批'`（派发自动审批，`remark = '派发自动审批'`） |

### 2.4 委外申请生成规则

| 规则 | 说明 |
|------|------|
| 触发条件 | 工艺路线明细 `is_outsourced = 1` 的工序 |
| 编号格式 | `OS-YYYYMMDD-NNN`，如 `OS-20260317-001` |
| 去重保护 | 同一生产单 + 同一工序号不会重复生成 |
| 初始状态 | `status = '未派发'`，`approval_status = '草稿'`（委外申请仍需人工审批后下发供方） |

### 2.5 排产冲突检查规则

派发执行前在事务内做两层冲突检查：

1. **本批次内冲突**：当前提交的 `items` 数组中，若存在两行的 `(equipment_number, production_date, schedule_id)` 完全相同，返回 **HTTP 400**。
2. **数据库已派发冲突**：对每个待派发项，查询 `production_order` 中同设备+同日期+同班次且 `plan_status IN ('已派发','已备料','生产中')` 的记录，若存在则返回 **HTTP 409**。

响应体中 `conflicts` 数组列出每条冲突的资源坐标与占用该资源的生产单号。

### 2.6 Baseline 基线记录规则

生产单**首次派发**时（`baseline_production_date IS NULL`），同步写入基线字段：

| 字段 | 取值来源 |
|------|----------|
| `baseline_production_date` | 本次派发的 `production_date` |
| `baseline_planned_completion_time` | 当前生产单的 `planned_completion_time` |

用于后续甘特图偏差分析、交期追溯。重新派发（如撤销后再次派发）不覆盖已存在的 baseline。

### 2.7 销售订单生产状态回写规则

派发成功后调用 `syncProductionStatus`，对生产单关联的销售订单明细行回写：

- 若销售订单明细的 `production_status` 当前为空或 `'未计划'`，更新为 `'计划中'`。
- 生产单完工后由完工流程进一步回写为 `'已完成'`（由其他流程负责，不在本派发范围）。

### 2.8 执行顺序依赖

> 工序任务**必须先于**备料单生成 —— 备料单明细的 `work_center_number` 字段需要从已生成的工序任务 / `routing_detail_material` 映射派生。

## 三、API接口设计

### 3.1 一键派发接口

```
POST /api/orders/dispatch-and-generate
```

**请求体：**

```json
{
  "items": [
    {
      "production_order_number": "P20260317001",
      "equipment_number": "EQ001",
      "equipment_name": "注射机1号",
      "mould_number": "MJ001",
      "formed_part_specifications": "10x10x5",
      "formed_part_unit_consumption": "0.5",
      "actual_cavity_count": "2",
      "actual_hole_count": "4",
      "actual_daily_output": "8",
      "production_date": "2026-03-17",
      "schedule_id": "SHIFT001"
    }
  ]
}
```

**成功响应体：**

```json
{
  "success": true,
  "message": "成功派发 3 条生产单",
  "data": {
    "dispatch": {
      "count": 3,
      "items": [
        { "orderNo": "P20260317001", "status": "dispatched" },
        { "orderNo": "P20260317002", "status": "dispatched" },
        { "orderNo": "P20260317003", "status": "dispatched" }
      ]
    },
    "processTasks": {
      "totalGenerated": 9,
      "details": [
        { "orderNo": "P20260317001", "tasksGenerated": 3 },
        { "orderNo": "P20260317002", "tasksGenerated": 4 },
        { "orderNo": "P20260317003", "tasksGenerated": 2 }
      ]
    },
    "materialPreparations": {
      "totalGenerated": 3,
      "details": [
        { "orderNo": "P20260317001", "materialsGenerated": 8 }
      ]
    },
    "outsourcingRequests": {
      "totalGenerated": 1,
      "details": [
        { "orderNo": "P20260317001", "reqNumber": "OS-20260317-001", "count": 1 }
      ]
    },
    "semiProductOrders": { "totalGenerated": 0, "details": [] },
    "errors": []
  }
}
```

> `semiProductOrders` 为**模具级MRP已取消后的兼容残留字段**，始终返回空数组，仅为前端旧逻辑兼容保留。

### 3.2 排产冲突错误响应

| HTTP状态码 | 触发场景 | 响应结构 |
|-----------|----------|----------|
| 400 | 本批次内排产冲突（提交数组内相互冲突） | `{ success:false, message, conflicts:[{ equipment_number, production_date, schedule_id, conflictWith:[...] }] }` |
| 409 | 数据库已派发记录冲突（资源被其他已派发生产单占用） | `{ success:false, message, conflicts:[{ resource, occupiedBy }] }` |
| 500 | 数据库事务异常 | 事务已自动回滚，返回异常信息 |

### 3.3 原有派发接口

```
POST /api/orders/dispatch
```

保留用于**仅派发状态更新、不生成任务**的场景（现已不是主流入口，生产端统一使用一键派发）。已含审批状态与计划状态双重校验。

## 四、数据库操作详解

### 4.1 第一步：派发生产单

**操作表：** `production_order`

```sql
UPDATE production_order SET
  plan_status = N'已派发',
  equipment_number = :equipment_number,
  equipment_name = :equipment_name,
  mould_number = :mould_number,
  formed_part_specifications = :formed_part_specifications,
  formed_part_unit_consumption = :formed_part_unit_consumption,
  actual_cavity_count = :actual_cavity_count,
  actual_hole_count = :actual_hole_count,
  actual_daily_output = :actual_daily_output,
  production_date = :production_date,
  schedule_id = :schedule_id,
  -- 首次派发时同步写入基线字段（若已存在则保留原值）
  baseline_production_date = COALESCE(baseline_production_date, :production_date),
  baseline_planned_completion_time = COALESCE(baseline_planned_completion_time, planned_completion_time)
WHERE production_order_number = :id
```

### 4.2 第二步：生成工序任务

**查询表：** `routing_header`、`routing_detail`、`routing_detail_material`
**写入表：** `process_task`、`outsourcing_req`、`outsourcing_req_detail`

**步骤：**

1. 匹配工艺路线主表（主路线优先）

```sql
SELECT TOP 1 process_route_number, process_route_name, bom_number
FROM routing_header
WHERE item_number = :item_number
  AND condition = N'启用'
  AND approval_status = N'已审批'
ORDER BY is_primary DESC, creation_date DESC
```

2. 读取路线明细（按工序号升序）

```sql
SELECT step_number, standard_process_number, standard_process_name,
  work_center_number, work_center_name, excess_reporting_ratio,
  ingredient_addition_method, process_material_input_number,
  process_material_input_quantity, process_material_input_unit,
  material_wastage_rate, operator, remark, is_outsourced
FROM routing_detail
WHERE process_route_number = :prn
ORDER BY step_number
```

3. 逐条插入工序任务（含去重），检测到 `is_outsourced = 1` 时同步写入委外申请

**字段映射：**

| process_task字段 | 数据来源 | 说明 |
|-----------------|----------|------|
| process_task_number | 自动生成 | PT-YYYYMMDD-NNN |
| production_order_number / production_number | 生产单 | 直接取值 |
| process_route_number | routing_header | 工艺路线编号 |
| step_number / standard_process_* | routing_detail | 工序信息 |
| item_number / item_name / specifications / basic_unit | 生产单 | 产品信息 |
| planned_quantity | 生产单 | 计划数量 |
| completed_quantity | 常量 | 初始值 0 |
| work_center_number / work_center_name | routing_detail | 工作中心 |
| process_material_input_* / material_wastage_rate | routing_detail | 物料投入 |
| operator | routing_detail.operator \|\| req.user.username | 优先工艺预设 |
| remark | routing_detail.remark | 工艺备注 |
| task_status | 常量 | "未开始" |
| approval_status | 常量 | **"已审批"**（派发自动审批，不再是"草稿"） |
| inspect_status | 常量 | "无需检" |
| creation_date / creation_man | 系统时间 / 当前用户 | 自动填充 |

**委外申请插入（仅 `is_outsourced = 1` 工序）：**

```sql
INSERT INTO outsourcing_req (outsourcing_req_number, production_order_number, ..., status, approval_status)
VALUES (:osNo, :poNo, ..., N'未派发', N'草稿')

INSERT INTO outsourcing_req_detail (outsourcing_req_number, step_number, ..., process_task_number)
VALUES (:osNo, :step, ..., :taskNo)
```

### 4.3 第三步：生成备料单

**查询表：** `bom_header`、`bom_detail`、`routing_detail_material`、`process_task`
**写入表：** `material_preparation`、`material_preparation_detail`

**步骤：**

1. 检查是否已有备料单（去重）
2. 匹配BOM主表（优先按 routing_header.bom_number）

```sql
-- 优先：按工艺路线关联的BOM
SELECT TOP 1 bom_number, bom_name, bom_version, base_quantity
FROM bom_header
WHERE bom_number = :routing_bom_number
  AND [condition] = N'启用'
  AND approval_status = N'已审批'

-- 回退：按产品编号
SELECT TOP 1 bom_number, bom_name, bom_version, base_quantity
FROM bom_header
WHERE item_number = :item_number
  AND [condition] = N'启用'
  AND approval_status = N'已审批'
ORDER BY bom_version DESC
```

3. **读取 BOM 第一层明细（不递归展开）**

```sql
SELECT line_number, material_number, material_name, specifications,
  standard_quantity, wastage_rate, step_number,
  is_key_material, supply_type, default_warehouse, basic_unit
FROM bom_detail
WHERE bom_number = :bom_number
ORDER BY line_number
```

4. 通过 `routing_detail_material` 建立"物料→工序→工作中心"映射；回退：使用 `bom_detail.step_number` 对应的工序任务
5. 计算需求量

```
倍率 = 计划数量 / BOM基数量
需求量 = 倍率 × 物料标准用量（四舍五入到4位小数）
```

6. 插入备料单主表 + 逐条插入明细；若明细写入失败，删除已插入的主表行保持一致性

**备料单主表字段映射：**

| 字段 | 来源 | 说明 |
|------|------|------|
| preparation_number | 自动生成 | MP-YYYYMMDD-NNN |
| production_order_number | 生产单 | 关联生产单 |
| bom_number / bom_version | bom_header | BOM信息 |
| planned_quantity | 生产单 | 计划生产数量 |
| bom_base_quantity | bom_header | BOM基数量 |
| total_material_types | 计算 | 明细行数 |
| preparation_status | 常量 | "未领料" |
| approval_status | 常量 | **"已审批"**（自动审批） |
| remark | 常量 | **"派发自动审批"** |

**备料单明细字段映射：**

| 字段 | 来源 | 说明 |
|------|------|------|
| line_number | 序号 | (index + 1) * 10 |
| material_number / material_name | bom_detail | 物料信息 |
| bom_standard_quantity | bom_detail.standard_quantity | BOM标准用量 |
| bom_wastage_rate | bom_detail.wastage_rate | 损耗率 |
| required_quantity | 计算 | 倍率 × 标准用量 |
| adjusted_quantity | 同上 | 初始值等于需求量 |
| issued_quantity | 常量 | 初始值 0 |
| step_number | routing_detail_material 映射 \|\| bom_detail.step_number | 关联工序 |
| work_center_number | 对应工序任务 | 由工序任务派生 |
| is_backflush | routing_detail_material.is_backflush | **倒冲标识**（新增） |
| is_key_material / supply_type / default_warehouse | bom_detail | 补充属性 |

### 4.4 第四步：销售订单回写

派发成功后在同一事务内调用 `syncProductionStatus(productionOrderNumber, transaction)`：

```sql
UPDATE sales_order_detail
SET production_status = N'计划中'
WHERE production_order_number = :poNo
  AND (production_status IS NULL OR production_status = N'' OR production_status = N'未计划')
```

## 五、前端交互设计

### 5.1 派发入口

**位置：** 生产单管理页面 `client/src/views/production/Order/List.vue`

**操作流程：**

1. 用户在生产单列表中勾选需要派发的记录
2. 点击"派发"按钮
3. 系统自动校验：
   - 所有选中记录的 `plan_status` 必须为"未开始"
   - 所有选中记录的 `approval_status` 必须为"已审批"
4. 打开派发对话框，展示可编辑的派发信息表格
5. 用户可以：
   - 批量设置设备、模具、生产日期、班次
   - 逐行修改每条记录的调度参数
   - 勾选设备后自动联动对应班次选项
6. 点击"确定派发"提交

### 5.2 派发确认

**确认对话框提示：**

> 将派发 N 条生产调度单，同时自动生成工序任务、备料单与委外申请（如有）。

### 5.3 结果展示

派发完成后弹出**结果展示对话框**，包含：

- **总览统计区域：** 统计卡片
  - 成功派发 X 条（绿色）
  - 工序任务 X 条（蓝色）
  - 备料单 X 份（紫色）
  - 委外申请 X 条（橙色，仅在有委外时显示）
  - 跳过 X 条（红色，仅在有跳过时显示）

- **详情折叠面板：** 每个生产单一个面板
  - 标题：派发状态标签 + 生产单号 + 工序/备料统计
  - 展开内容：工序任务、备料单、委外申请的具体生成结果或跳过原因

- **冲突告警区域：** 若后端返回 400/409，展示冲突资源坐标和占用该资源的生产单号
- **错误告警区域：** 未能派发的生产单及其原因列表

### 5.4 前端校验逻辑

```typescript
// 检查计划状态
const invalidRecords = selectedRowKeys.value.filter(key => {
  const record = dataSource.value.find(d => d.production_order_number === key)
  return record && record.plan_status !== '未开始'
})
if (invalidRecords.length > 0) {
  message.warning('只能派发状态为"未开始"的记录，请重新选择')
  return
}

// 检查审批状态
const unapprovedRecords = selectedRowKeys.value.filter(key => {
  const record = dataSource.value.find(d => d.production_order_number === key)
  return record && record.approval_status !== '已审批'
})
if (unapprovedRecords.length > 0) {
  message.warning('只能派发审批状态为"已审批"的记录，请先完成审批')
  return
}
```

排产冲突检查由后端权威执行（避免前后端数据不一致），前端仅在响应 400/409 时展示错误告警。

## 六、事务与异常处理

### 6.1 事务策略

所有操作统一通过 `orderDispatch.service.ts` 的 `dispatchAndGenerateCore` 在 `withTransaction` 包裹下执行：

- 排产冲突检查、生产单UPDATE、工序任务INSERT、委外申请INSERT、备料单INSERT、销售订单回写 **共享同一事务**
- 任何数据库异常导致事务回滚，所有更改撤销
- 单个生产单的工序/备料/委外生成异常被捕获为 `errors` 项，不影响其他生产单的派发（跳过策略）

### 6.2 容错机制

| 场景 | 处理方式 |
|------|----------|
| 生产单不存在 | 跳过，记录错误信息 |
| 审批状态不符 | 跳过，记录错误信息 |
| 计划状态不符 | 跳过，记录错误信息 |
| 本批次内排产冲突 | **整体返回 HTTP 400**，事务回滚 |
| 数据库已派发冲突 | **整体返回 HTTP 409**，事务回滚 |
| 无匹配工艺路线 | 派发成功，工序任务标记为跳过 |
| 工艺路线无明细 | 派发成功，工序任务标记为跳过 |
| 工序任务已存在 | 自动跳过该工序（幂等） |
| 工序含 is_outsourced 但无委外模板 | 派发成功，委外申请标记为跳过 |
| 无匹配BOM | 派发成功，备料单标记为跳过 |
| BOM无第一层明细 | 派发成功，备料单标记为跳过 |
| 备料单已存在 | 自动跳过（幂等） |
| 备料单主表成功但明细失败 | 清理孤立主表，标记为错误 |
| 销售订单回写失败 | 不影响派发主流程，记录警告 |
| 数据库事务异常 | 全部回滚 |

## 十一、与原方案（v1.0）主要差异

### 11.1 业务规则增强（非破坏性变更）

| 项目 | v1.0 设计 | v2.0 实现 |
|------|-----------|-----------|
| 工序任务审批状态 | 草稿 | **已审批**（自动审批） |
| 备料单审批状态 | 草稿 | **已审批**（`remark = '派发自动审批'`） |
| 排产冲突检查 | 未提及 | 本批次 + 数据库双层冲突检查（400/409） |
| Baseline 记录 | 未提及 | 首次派发时记录基线字段 |
| 销售订单回写 | 未提及 | `production_status` 回写为"计划中" |
| 委外申请自动生成 | 未提及 | 检测 `is_outsourced` 工序自动生成委外申请 |
| 备料单清理机制 | 未提及 | 主表插入成功但明细失败时自动清理 |
| 倒冲字段 | 未涉及 | 新增 `is_backflush` 透传 |

### 11.2 实现简化

> **BOM 展平：** v1.0 要求递归展平多级BOM（最大深度10层）。v2.0 当前实现**仅取 `bom_detail` 第一层明细**，不做递归展开。若产品BOM包含子BOM（半成品又有自己的BOM），子BOM中的物料不会被自动展开到备料单；需依靠主数据层面维护扁平化的生产BOM结构。

### 11.3 已取消功能残留

> 响应结构中保留 `semiProductOrders: { totalGenerated: 0, details: [] }` 字段，这是**模具级MRP重算功能取消**后的残留，始终返回空数组，不影响业务功能，仅为前端旧逻辑兼容保留。

### 11.4 字段映射差异

| 字段 | v1.0 设计 | v2.0 实现 |
|------|-----------|-----------|
| `process_task.remark` | 空 | 取 `routing_detail.remark` |
| `process_task.operator` | 未明确 | `routing_detail.operator` 优先，回退当前登录用户 |
| 备料单 BOM 匹配 | 按产品编号 | **优先按 `routing_header.bom_number`**，回退产品编号 |
| 备料单 `step_number` | `bom_detail.step_number` | **优先从 `routing_detail_material` 映射**，回退 `bom_detail` |
| 工艺路线排序 | `creation_date DESC` | **`is_primary DESC, creation_date DESC`**（主路线优先） |
