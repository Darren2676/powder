# MES 系统事件驱动架构评估报告

> 评估范围：后端服务跨模块业务触发机制（报工 → 库存更新 + 质量检查等链路）
> 评估日期：2026-03-17

---

## 一、现状结论：当前系统完全没有消息队列或事件总线

经过对后端全量代码扫描，确认现状如下：

| 组件 | 是否存在 | 说明 |
|------|----------|------|
| RabbitMQ / Kafka / Redis PubSub | ❌ 无 | 没有任何消息中间件依赖 |
| Bull / Bee-Queue / Agenda | ❌ 无 | 没有任何任务队列库 |
| Node.js EventEmitter 自定义总线 | ❌ 无 | 没有进程内事件机制 |
| 数据库触发器 / Hook | ❌ 无 | 无 SQL Server trigger 或 ORM hook |
| 定时任务 / Cron | ❌ 无 | 无 setInterval、node-cron 等 |

---

## 二、跨模块通信现状：全部同步强耦合调用

以**报工完成 → 触发库存更新 + 质量检查**为例，当前链路如下：

```
workReport.service.ts (报工)
  │
  ├──► syncTaskCompletion()          ← 直接调用，更新工序/生产单状态
  │
  ├──► logWorkReportLinesideMovement() ← 直接调用，线边仓流转
  │
  ├──► autoCreateInspections()       ← 直接调用
  │       │
  │       └──► import { createInspectionFromWorkReport }
  │             from '@/modules/quality/productionInspection/controller'
  │             ← 生产模块直接导入质量模块的 Controller
  │
  └──► syncProductionStatus()        ← 直接调用，回写销售订单
```

**所有操作共享同一个数据库事务**，串行同步执行。

### 关键代码证据

**`server/src/services/workReport.service.ts` 第 361-367 行：**

```typescript
// 立即同步工序任务完成数量（草稿状态即计入）
await syncTaskCompletion(task.process_task_number, qualifiedQty, transaction);

// 线边仓流转记录
await logWorkReportLinesideMovement(task.process_task_number, qualifiedQty, wrNumber, user?.username || '', transaction);

// 自动创建检验记录
await autoCreateInspections(task.process_task_number, wrNumber, qualifiedQty + unqualifiedQty, user?.username || '', transaction);
```

**`server/src/services/workReport.service.ts` 第 12 行：**

```typescript
import { createInspectionFromWorkReport } from '@/modules/quality/productionInspection/productionInspection.controller';
```

生产模块的服务层直接导入质量模块的 Controller，模块边界被破坏。

---

## 三、现有唯一接近"事件"的机制：审批回调钩子

系统有 `workflow.hooks.ts` + `approval.service.ts`，提供了审批流的回调注册：

```typescript
// workflow.hooks.ts
export async function executeModuleHook(
  module: string,
  hookType: 'onApproved' | 'onRejected',
  recordId: string
): Promise<void> { ... }
```

但这**仅限于审批状态变更**（`onApproved` / `onRejected`），不能用于通用业务事件（如报工完成、入库完成、检验完成）。

---

## 四、当前架构的核心风险

| 风险点 | 具体表现 |
|--------|----------|
| **模块边界破坏** | `workReport.service.ts` 直接 `import` 质量检验的 `controller`，违反分层架构 |
| **事务膨胀** | 报工 + 状态同步 + 线边仓 + 检验创建全部绑在一个事务，任何一环失败整体回滚 |
| **性能瓶颈** | 同步串行执行，报工响应时间 = 各步骤耗时累加，高并发时事务锁竞争加剧 |
| **扩展困难** | 新增"报工后触发 X"（如自动通知、成本核算），必须修改报工源码，违反开闭原则 |
| **单点故障** | 若质量检验模块临时异常，报工也会失败，导致生产现场无法报工 |

---

## 五、改进建议：渐进式事件驱动方案

根据当前单体架构、单进程部署的现状，建议分三阶段落地：

### Phase 1：进程内 EventBus（建议立即实施）

引入 Node.js 原生 `EventEmitter`，零依赖、改动最小：

```typescript
// shared/eventBus.ts
import { EventEmitter } from 'events';
export const eventBus = new EventEmitter();
```

**核心领域事件定义：**

| 事件名 | 触发时机 | 消费者 |
|--------|----------|--------|
| `WorkReportCreated` | 报工单创建完成 | 质量模块（创建检验记录）、库存模块（线边仓流转） |
| `TaskStatusChanged` | 工序任务状态变更 | 生产计划模块（更新生产单状态） |
| `InspectionFinished` | 检验记录完成判定 | 生产模块（回写工序检验状态）、库存模块（更新质量状态） |
| `StockInCreated` | 入库单创建完成 | 库存模块（更新批次/汇总库存）、财务模块（会计期间记录） |

**改造报工服务：**

```typescript
// 改造前：直接调用
await autoCreateInspections(taskNo, wrNumber, qty, user, transaction);

// 改造后：发布事件
eventBus.emit('WorkReportCreated', {
  taskNo, wrNumber, qty, user, transaction
});
```

**各模块独立订阅：**

```typescript
// quality/productionInspection/subscriber.ts
import { eventBus } from '@/shared/eventBus';

eventBus.on('WorkReportCreated', async (payload) => {
  await autoCreateInspections(payload);
});

// warehouse/linesideMovement/subscriber.ts
eventBus.on('WorkReportCreated', async (payload) => {
  await logWorkReportLinesideMovement(payload);
});
```

**优势：**
- 解耦模块，报工服务不再依赖质量/库存模块
- 支持事务内发布（事务提交后再真正触发异步逻辑）
- 零运维成本，无需新增中间件

### Phase 2：数据库事件表（核心流程防丢失）

对**库存更新、财务记账**等不能丢失的事件，引入数据库事件表：

```sql
CREATE TABLE system_events (
  id BIGINT IDENTITY PRIMARY KEY,
  event_type NVARCHAR(100),
  payload NVARCHAR(MAX),
  status NVARCHAR(20), -- pending / processing / completed / dead
  retry_count INT DEFAULT 0,
  created_at DATETIME DEFAULT GETDATE(),
  processed_at DATETIME
);
```

**流程：**
1. 业务事务中 `INSERT INTO system_events`
2. 事务提交后，后台 worker 轮询消费
3. 消费成功 → `status = completed`
4. 消费失败 → `retry_count++`，达到阈值 → `status = dead`

### Phase 3：Redis Pub/Sub（预留分布式扩展）

未来若拆分为微服务或多实例部署，保持 EventBus 接口不变，底层替换为 Redis adapter：

```typescript
// 接口不变，仅切换实现
if (process.env.REDIS_URL) {
  eventBus = new RedisEventBus(); // 跨进程
} else {
  eventBus = new LocalEventBus(); // 单进程
}
```

## 六、推荐优先级

| 优先级 | 事项 | 预期收益 | 预估工作量 |
|--------|------|----------|------------|
| **P0** | EventBus + 报工/检验/库存事件改造 | 解决模块耦合、事务膨胀、单点故障 | 2-3 天 |
| **P1** | 数据库事件表 + 补偿机制 | 防止事件丢失，支持失败重试 | 1-2 天 |
| **P2** | 现有审批钩子迁移到 EventBus | 统一事件体系，消除双轨制 | 0.5 天 |
| **P3** | Redis Pub/Sub 适配层 | 为微服务拆分预留能力 | 1 天 |

---

## 七、总结

当前系统**不具备任何消息队列或事件总线能力**，跨模块业务触发完全依赖同步函数调用，这在报工 → 检验 → 库存 → 销售订单的链路中已经造成了明显的耦合和可靠性问题。

建议**立即启动 Phase 1（进程内 EventBus）**，将 `workReport.service.ts` 中的 `autoCreateInspections`、`syncTaskCompletion`、`logWorkReportLinesideMovement` 等硬编码调用改造为事件发布/订阅模式。这是成本最低、收益最明确的改进路径。
